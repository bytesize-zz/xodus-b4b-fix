## Why change the original implementation?

The original watcher recursively monitored the whole games parent and copied
one bundled executable over any newly created/moved file with the EAC setup
filename. This could affect unrelated games or originals reached through
symlinks/hardlinks. Its generated desktop launcher also failed on paths with
spaces. These changes preserve the intended B4B chain replacement while making
the target selection explicit and testable.

## Changes and rationale

- Restrict candidates to immediate `.xodus-chain-*` directories and validate
  all three B4B deployment IDs, the game executable marker, and a recognized
  input hash. Other games and unknown revisions are left untouched.
- Use descriptor-relative nofollow traversal and atomic new-inode replacement
  to avoid writing through symlinks or modifying hardlinked originals.
- Accept Xodus's real settings-file symlink layout only when the link points
  to the explicitly selected game's settings. Read that trusted target with
  nofollow checks; do not relax protection on write destinations.
- Use Python's standard library and Linux inotify instead of recursively
  invoking inotifywait. Handle close-write/moved-to events and rescan new
  directories; report readiness and fatal watcher failures explicitly.
- Ignore regular companion lock files and transient missing assembly files.
  Emit one WAIT notice after 10 seconds of incompleteness, while retaining
  validation warnings and retrying. This avoids false-error startup noise.
- Require an explicit game path and bundled-file acknowledgment. Never run
  sudo, install packages, or launch the bundled EXE during installation.
- Preserve existing runtime.conf, back up replaced helper files, install
  independent copies, and correctly quote shell/Desktop Entry arguments.
- Pin bundled hashes and retain the successful Authenticode verification
  report. A hash pin is not provenance; the EXE signature does not establish
  runtime.conf authenticity or publisher approval of this workaround.
- Add 24 automated tests covering real inotify events, staged assembly,
  supported settings links, unsafe filesystem objects, unknown versions,
  original-file preservation, installation/reinstallation, and path quoting.
- Document installation, removal, trust boundaries, and timing limitations.
  The original PR_PLAN.md remains historical proposal material.

## Remaining limitations

There is still a launch-time race: inotify plus a 300 ms stability interval
cannot guarantee replacement before the game reads the file. An integrated
Xodus chain-assembly hook would be needed for a guaranteed handoff. This is not
a security boundary against a hostile same-user process. Installation is atomic
per file, not transactional as a whole. runtime.conf authenticity has not been
independently verified; future compatibility and account safety are not promised.

Other EAC games are intentionally unsupported. Future expansion should use
per-game profiles with separately validated IDs, layouts, input hashes and
replacement files, rather than restoring filename-only global replacement.
